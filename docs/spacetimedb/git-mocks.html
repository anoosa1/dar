Git — repositories and commits mocks

A Git app in the unified frame, in the spirit of Gitea, over what Dar already stores: every Files folder that keeps history is a repository, cloned and pushed at /dav/git/<folder>.git with an app password. The app owns no data of its own. It reads the folder’s commits, branches and tags and the cached Git objects, and its actions (track, commit, restore, delete a branch) are the folder history operations Files already has. Two directions differ in the home screen and in how a repository’s commits are shown; the frame, sidebar, repository tabs and commit details are shared.

  • A · Repository list, Gitea-style tabs: home is a list of repositories with their description, last update, counts and activity; a repository opens on Code (files at a branch with the README below), then Commits, Branches and Tags. A commit opens in the right sheet with its diff.
  • B · Activity overview, commit graph: home is a year of activity, repository cards and a feed of pushes, Dar commits and Agent merges across repositories; Commits draws the branch graph so merges and open branches read at a glance.
  • Shared: the description is the README’s first paragraph; the clone address uses the folder ID so renaming or moving the folder never breaks a remote; commits show where they came from (Git push, Dar or Agent) and their Git ID; Agent branches link to their Agent thread and stay read-only here, as they are for pushes.
  • Not in scope: issues, pull requests, CI, forks, stars and web editing; files are edited in Files. Branch compare and ZIP downloads are new reads over the existing objects; merging a branch from the web is an open question.

A1 · Repositories — light

Home lists every folder that keeps history, newest activity first: the README’s first paragraph, counts, last update, history storage and 12 weeks of commits. A row marks uncommitted Dar changes. The selected repository opens in the right sheet with its clone address, quick actions and facts.
